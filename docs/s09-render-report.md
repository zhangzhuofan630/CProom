# S0.9 渲染器实测报告

> 日期：2026-10-28
> 结论：**GO**。QWidget + QPainter 软件合成满足「空闲 CPU < 1%、内存 < 150MB」，
> 不需要为了性能提前引入 QML / OpenGL。
>
> 但有一个代价必须记住：**头部旋转是逐帧像素重采样**，它占了活动状态下一半的 CPU。
> 详见第四节。

---

## 一、为什么这个测试不能省

web demo 跑到了 60fps，但那**不能作为依据**——Canvas 2D 走浏览器的 GPU 合成，
QPainter 默认走纯 CPU 光栅。两套后端，同一段绘制逻辑的性能可以差一个数量级。

所以 S0.9 的硬指标必须在 Qt 里真跑一遍。这里的每个数字都是 `--bench` 模式
自测的（进程 CPU 时间 / 墙钟时间），不是外部 `top` 观察的区间均值。

---

## 二、实测数据

环境：Ubuntu 22.04 / KDE Plasma（XWayland）/ 1920×1080 / 16 核
方法：每种配置跑 10 秒，取两次结果

| 场景 | 帧率 | CPU | 内存(RSS) | 判定 |
|---|---|---|---|---|
| 空闲（只有呼吸 + 偶尔眨眼） | 8 fps（眨眼时临时提帧） | **0.33 %** | **55 MB** | ✅ 达标 |
| 空闲（idle 提到 15 fps） | 15 fps | 0.53 % | 55 MB | ✅ 达标但没必要 |
| 持续跟随鼠标 | 30 fps | 1.98 % | 55 MB | 可接受 |
| 持续跟随鼠标 | 20 fps | **1.36 %** | 55 MB | **默认值** |
| 持续跟随鼠标 | 15 fps | 1.05~1.48 % | 55 MB | 开始有顿感 |

指标来自 `docs/plan-review.md`：空闲 CPU < 1%，内存 < 150MB。

内存比 web 版高不少，主要是 Qt 自身 + X11 后端 + 字体系统的固定开销。
离 150MB 的线还有近 3 倍余量。

### 每帧成本拆解

- 空闲：0.33 % ÷ 9.4 fps ≈ **0.35 ms/帧**
- 跟随：1.36 % ÷ 19.3 fps ≈ **0.70 ms/帧**

差值 0.35ms 就是「头部旋转」的价格。这个数字决定了下一步的技术方向，见第四节。

## 三、四个非显然的发现

### 1. 呼吸用 scale 做，会让四层每帧都重采样

第一版呼吸是「绕底边中点缩放 1.008」，看起来是「身体微微起伏」。实测空闲 0.62%。

改成「整体上下来回平移 1.8px」后降到 **0.33%**，几乎腰斩。

原因：`p.scale()` 之后每一次 `drawPixmap` 都会走双线性重采样，四层全部重采样一遍。
而平移是 1:1 blit，零重采样。视觉上平移反而更像呼吸——呼吸本来就是重心起伏，
不是体积膨胀。

**在软件光栅里，任何非恒等变换都要付出整层重采样的代价。**

### 2. 达标靠的是动态帧率，不是降帧率

第一版固定 15fps，实测 1.22%，超标。

改成「静止 8fps / 有动作 20fps」后空闲 0.33%。关键不是平均帧率低，而是
**只在画面真的变了的时候才画**：静止时只有呼吸在动，8fps 完全看不出跳动
（呼吸周期 4.2 秒，每帧相位差 10°）；一旦头部在追、在跳、在眨眼，立刻切满帧。

眨眼还额外需要处理：140ms 的眨眼在 8fps 下只有 1 帧，会被吞掉。所以
`setExpr()` 里对短表情直接强制提帧，不等下一 tick 生效。

### 3. 窗口尺寸由「旋转扫过的区域」决定，不是角色包围盒

角色静止时只占 141×238，但窗口是 202×267——多出来的全是留给头部旋转的。

第一版想省掉这块空白，直接按静止包围盒裁剪，结果**头一转就把头发削掉一块**。
正确做法是把 head 层绕颈部旋转 ±12° 后扫过的 bbox 并进裁剪框：

```
裁剪框 = 四层静止包围盒 ∪ (head 包围盒绕 neck 旋转 ±12° 后的包围盒)
```

这条约束必须和渲染时的角度限幅**同源**（`PetPack::kMaxHeadAngleDeg`），
否则改了限幅忘了改裁剪，就会静默裁图。

顺带一提：原画布里角色是偏左的（左边空 29px、右边空 39px），直接当窗口用
会让人以为桌宠没贴到右下角。按包围盒裁剪顺带修掉了这个视觉问题。

### 4. 表情补丁必须跟着头部一起变换

表情是独立一层，z-order 在 head 之上。它必须画在 head 的变换坐标系里：

```cpp
p.translate(center + off, neckY + offY);
p.rotate(angle);
p.translate(-center, -neckY);
drawPixmap(head);
drawPixmap(expr);   // ← 在同一变换里
p.restore();
drawPixmap(collar); // ← 不跟头动，画在外层
```

如果忘了在变换内画表情，头一转眼睛就留在原地。

## 四、渲染选型结论（S0.8 的答案）

**这一版够用，先不换 QML。**

但要知道代价在哪：

| | QWidget + QPainter（现状） | QML Scene Graph |
|---|---|---|
| 头部旋转 | 逐帧像素重采样，占活动 CPU 约一半 | 顶点变换，接近免费 |
| 活动 CPU | 1.36 %（20fps） | 预计 < 0.5% |
| 空闲 CPU | 0.33 % | 可能更高（合成器常驻） |
| 代码复杂度 | 低，无 QML 运行时 | 需要 QML + C++ 边界 |
| Wayland 透明/置顶 | 走 Qt 的通用路径，与 QML 相同 | 同左 |

关键判断：**指标已经达标，没有理由为了 1% 的 CPU 引入 QML 运行时和一层
语言边界的复杂度。** 等真的需要「头发飘动」「多角色」这类场景再换。

如果将来必须优化，最便宜的一招不是换框架，而是**预渲染角度档位**：
把 head 层预先旋转成 -12/-8/-4/0/+4/+8/+12 七张，运行时按最近角度选用，
用 4° 的离散化换掉每帧重采样。代价是 7 张 head（约 0.5MB）和可能可见的角度跳变。
这个方案还没做，留作备选。

## 五、验证边界（没证明的事）

诚实记录，避免下一轮误以为已经验证过：

1. **没有程序化截屏验证真实屏幕内容。** 本机是 KDE + XWayland，`xwd`/`import`
   抓根窗口都返回 `BadMatch`（XWayland 的 root 只是 Wayland 的一个 surface）。
   所以真实屏幕上的像素长什么样**没有截图为证**，只有：
   - 程序自己 `render()` 出的图（`--snapshot`），确认分层合成、旋转、表情都正确
   - `xwininfo` 确认窗口存在：202×267、Depth **32**（ARGB，真透明）、
     `Map State: IsViewable`
   - `xprop` 确认 `_NET_WM_STATE_ABOVE`（置顶）、`SKIP_TASKBAR`（不占任务栏）

2. **只在 XWayland 后端测过。** 原生 Wayland（`QT_QPA_PLATFORM=wayland`）
   没测。按之前的调研，Wayland 下置顶基本无效，需要走 layer-shell，那是 Phase 1 的事。

3. **没测多显示器、没测 DPI 缩放、没测开机自启。**

4. **没测 Windows。** 代码里 Windows 分支（`metrics.cpp` 的 `GetProcessTimes` /
   `GetProcessMemoryInfo`）是照着文档写的，没有在 Win11 上编译过。CI 只能验证编译。

## 六、用法

```bash
# 普通模式：桌宠出现在屏幕右下角
./build/bin/desktop

# Wayland 桌面下必须强制走 X11，否则置顶无效
QT_QPA_PLATFORM=xcb ./build/bin/desktop

# 性能自测（跑 10 秒后打印结果并退出）
./build/bin/desktop --bench 10

# 测「一直在跟鼠标」的 CPU 上界
./build/bin/desktop --bench 10 --animate

# 渲染一帧到文件，核对分层是否正确
./build/bin/desktop --snapshot /tmp/pet.png --snap-angle 12 --snap-expr happy
```

参数：`--pack`（默认 `~/AI/petpack`）、`--width`（显示宽度，默认 200）、
`--fps`（有动作时，默认 20）、`--idle-fps`（默认 8）。

**素材不在仓库里。** `~/AI/petpack` 是本地生成目录，含人脸相关素材，
`.gitignore` 已排除所有 `*.jpg`。程序启动时如果找不到素材会给出明确提示。

## 七、已知缺陷

1. **没有手臂层**——「挥手」做不了，这是桌宠最高频的动作
2. **没有骨架、没有关键帧**——动作都是代码里硬写的位移/旋转，不是 petpack 里描述的动画系统
3. **头部旋转看起来像平移**——头太大，绕颈部转 12° 头顶要移动 30+px，视觉上不像「转头」像「头在滑」。可能需要降到 ±8°
4. **下巴与领口在极端角度仍有缝**——衣领遮罩能盖住 ±12° 内的缺口，超过就露背景
5. **没有拖拽、没有右键菜单、没有托盘**

## 八、下一步

渲染性能这个不确定性已经消掉了。接下来按价值排序：

1. **拖拽 + 落地物理**——桌宠最基本的手感，不做这个没法给女朋友用
2. **补手臂层**——重新生成一张手臂分开的素材，让「挥手」成立
3. **把动作从代码搬到 petpack**——`animations/*.json` 现在还是空的，渲染器里是硬编码
4. **Wayland 适配**——至少让 `QT_QPA_PLATFORM=xcb` 这件事自动化，用户不该知道这个
