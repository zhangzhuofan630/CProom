# 情侣桌宠项目方案评估

> 评估对象：用户提供的 15 步实施方案（原方案，见文末附录要点）
> 评估日期：2026-10-28
> 结论摘要：**方向正确，但有 4 个结构性问题会导致返工，其中 1 个必须在写代码前解决。**

---

## 一、总体判断

### 做对的部分（应保留，不要改）

| 原方案做法 | 评价 |
|---|---|
| 先做离线桌宠引擎，再接 AI | 正确。AI 不可用时核心功能仍可用，这是产品底线 |
| AI 只产出角色素材，引擎不绑定特定模型 | 正确且关键。适配器抽象是必须的 |
| 照片不上传 GitHub、不打包进安装文件 | 正确 |
| 动作模板化 / 预制骨架，不让模型自由生成多帧 | **思路完全正确**，但落地方式需要改（见问题二） |
| 模型密钥只在服务端 | 正确 |
| Ubuntu Wayland 提供兼容模式而非硬扛 | 正确，且比大多数人清醒 |

### 问题分布

- **1 个顺序问题**（问题一）：AI 生成验证被排到了第 10 步之后，太晚
- **2 个架构问题**（问题二、三）：素材格式与生成管线的耦合方式不对
- **1 个范围问题**（问题四）：后端服务建得过重，且与"隐私优先"自相矛盾
- **若干遗漏项**：见第五节

**核心判断：原方案把"最难、最不确定"的 AI 一致性验证放在了第 12 步，而第 4 步就要冻结 `petpack` 格式定义。** 这两件事之间隔了 8 步。一旦第 12 步发现生成出来的角色无法套进既定格式，第 4~8 步的引擎、素材、动作模板全部要推翻。这是整个方案最大的风险点。

## 二、问题一：顺序 —— AI 一致性验证必须前置到 Sprint 0

### 原方案的问题

原方案在第 12 步才做「自动变为桌宠」，在第 9~11 步才做「照片生成」。而第 4 步就定义了 `petpack` 格式：

```
character.json     角色名称、风格、版本、动作列表
sprites/           精灵图或 WebP 动画帧
animations/        待机、走路、睡觉等定义
```

`sprites/` 是**帧序列**格式。而第 12 步想做的事是「AI 生成并确定角色外观 → 映射到统一的身体比例、锚点、发型和服饰模板 → 基于预制动作骨架或精灵图模板生成动作」。

这里有一个未言明但致命的前提假设：**「同一个人生成的多个动作帧，看起来是同一个人」**。

这是当前图像生成模型最难的问题之一。扩散模型逐帧独立生成时，即使锁定 seed、锁定提示词、同一张参考图，脸型、发型走向、衣服配色依然会漂移。原方案第 6 步用"手工素材"绕开了这个问题（人工画当然一致），但第 11~12 步要把 AI 角色送进同一套 `petpack`，这个矛盾就暴露了。

**如果到第 12 步才发现，petpack 的 `sprites/` 帧序列结构不成立，需要改成骨架+分层结构，那么第 4~8 步的动画引擎、动作模板、双宠逻辑全部要重写。** 这是 8 步的返工。

### 修正方案：Sprint 0（1~2 周，只出结论不写 App 代码）

在动引擎之前，先用最低成本验证三件事：

**验证项 A：单张"照片 → Q版角色图"是否稳定可行？**

- 工具：ComfyUI + SDXL/Flux + IP-Adapter（或 InstantID）做面部特征保持
- 输入：3~5 张同一人的正脸照片
- 输出：1 张 Q 版角色立绘
- 判定：能否稳定保留可辨识的面部特征（发型、脸型、眼镜、配饰）

**验证项 B：能否生成"多姿势但同一角色"？**

- 方案一（推荐先试）：用 ControlNet 的 OpenPose 控制姿态，锁定同一 seed 与同一 LoRA/IP-Adapter 权重，生成行走/坐下/睡觉等姿势
- 方案二（更稳）：**不要生成多张图，而是生成一张角色，再由程序做骨骼变换驱动**（见问题二）
- 判定：10 张图里，有几张能被认出是同一个人

**验证项 C：动作框架到底该长什么样？**

基于 A、B 的结果，确定 `petpack` 是"帧序列"还是"分层 + 骨架"。**这个结论必须在写引擎之前拿到。**

**Sprint 0 的产出物**：
1. 一份技术选型结论（ComfyUI + 哪个底模 + 哪个 IP-Adapter 方案）
2. 一套可复现的工作流（ComfyUI workflow JSON）
3. `petpack` 格式 v0.1 草案
4. 10~20 张测试生成图（好坏的都要留档）

**Sprint 0 的价值**：花 1~2 周，买掉"第 4~8 步全部返工"的风险。这笔交易无论结果如何都划算——如果验证失败，你只损失 2 周，而不是 3 个月。

## 三、问题二：架构 —— `petpack` 应为"分层 + 骨架"，而非"帧序列"

### 两种方案对比

**方案 A：帧序列（原方案）**
```
sprites/idle_00.png, idle_01.png, ...
animations/idle.json → 帧列表 + 帧时长
```
- 优点：引擎简单，纯贴图动画，美术直接产出
- 致命缺点：**每增加一个角色，每个动作，每种画风，就要重新出一整套帧**。AI 生成的角色还必然串脸。双宠 × 2 角色 × 8 动作 = 32 组帧，制作成本爆炸

**方案 B：分层 + 骨架（推荐）**
```
character.json     角色元数据、骨架定义
layers/            body.png, head.png, hair_back.png, hair_front.png, arm_l.png, arm_r.png, eye_l.png, eye_r.png, mouth.png
rig.json           锚点表：每个部件在基准坐标系的锚点、旋转中心、层级
animations/idle.json → 关键帧变换序列（部件名 + 位移/旋转/缩放/透明度）
```
- 优点：
  - **AI 只生成一次外观**（切好的分层 PNG），动作全部由骨骼变换驱动 → 一致性天然保证，从根上消除串脸问题
  - 一套动作模板可套用在任意角色上（这是原方案第 12 步想要的"统一身体比例、锚点"效果，但用骨架实现才成立）
  - 资产量小：8 个动作 ≈ 8 个 JSON，而不是 32 组 PNG
  - 后续加表情、加配件（帽子/眼镜/围巾）只需替换单个 layer
- 代价：需要实现骨骼变换与渲染层；美术素材需要按规范切图

### 关键洞察

**原方案第 12 步的"统一身体比例、锚点、发型和服饰模板"，本质上就是一套骨架系统。** 既然要实现它，就应该在第 4 步就把 `petpack` 定义成分层+骨架结构，而不是等到第 12 步再补。这样：

- 第 6 步的手工素材也按分层规范产出（甚至可以写个切图辅助工具）
- 第 12 步的"自动转桌宠"变成「AI 生成外观 → 自动切层 → 自动绑定锚点 → 输出 petpack」，其中**"自动切层 + 自动绑定锚点"是纯代码工作，不需要模型**，可控性远高于"让模型生成多帧"

### 自动切层的可行性

Q 版角色图的自动分层有成熟方案可用：
- `rembg` / `U2Net` 做前景抠图
- `SAM`（Segment Anything）按提示分割出头发、脸、身体、手臂
- 或直接用固定槽位模板生成（见下）

**更稳的做法**：不依赖事后切分，而是**先准备一张"分层槽位参考图"**（标注好每个部件该出现在哪里），用 ControlNet 的 inpainting 逐个部位生成。这样每个部件的位置和尺寸都是被约束住的，绑定锚点变成确定性操作。这比"生成整图再切"稳定得多。

### 建议的分层结构

```
character.json
  name, style, version
  canvas: { width, height }
  anchor_reference: "slots.png"      # 槽位参考图
layers/
  body.png      hair_back.png   hair_front.png
  head.png      eye_l.png       eye_r.png
  mouth.png     arm_l.png       arm_r.png
  leg_l.png     leg_r.png       accessory_*.png
rig.json
  bone_hierarchy: [ { id: "root", parent: null, pivot: [x,y] }, ... ]
  layer_anchors: { "hair_front": { bone: "head", offset: [x,y] }, ... }
  z_order: [ "hair_back", "leg_l", "leg_r", "body", "head", "arm_l", "arm_r", "hair_front" ]
animations/
  idle.json  walk.json  sleep.json  drag.json  click.json  ...
  # 每个文件 = 关键帧列表 [{ t, targets: { "arm_l": {rot, dx, dy, scale, alpha} } }]
```

## 四、问题三：范围 —— 后端服务建得过重，且与隐私承诺矛盾

### 原方案第 10 步的问题

原方案要求搭：
```
Qt 客户端 → API 服务（鉴权、限流、隐私规则、任务创建）
           → Worker（调用云模型或本地生成引擎）
           → 临时对象存储（短期保存照片与候选结果）
```
再加上第 13 步的"本地模型选项"。

问题有三个：

**1. 对个人项目，这是过重的运维负担。** 鉴权、限流、对象存储过期清理、并发控制、密钥轮换——这些是**有付费用户的 SaaS 才需要**的。首版只有你和女朋友两个人用，为两个人维护一套服务端是纯负担。

**2. 与"隐私优先"自相矛盾。** 原方案第 0 步承诺「照片不上传」，第 10 步却把「临时对象存储」设计成了必经之路。照片要上传到服务器、落盘、等待过期删除——这个链路本身就有泄露风险，而且你需要自己保证删除逻辑真的正确。

**3. 逆了优先级。** 原方案把「本地模型选项」放在第 13 步（倒数第二），把「云端服务」放在第 10 步。但对桌宠这个场景，**本地生成才是主路径，云端是可选加速**。

### 修正方案：本地优先，云端作为可选适配器

```
桌面客户端
  → 生成适配器接口（统一 API）
      ├─ ComfyUI 适配器（本地，http://127.0.0.1:8188）  ← 默认，隐私最好
      ├─ 云端 API 适配器（可选，用户自备 key）            ← 后续
      └─ 手动导入 petpack（永远可用）                     ← 兜底
```

具体调整：

- **第 9 步（生成页面）提前到 Phase 2**，但要重新定位：它不是"上传到我们的服务"，而是"连接到你自己的生成后端"
- **第 10 步大幅简化**：不建对象存储。生成中间产物直接落本地临时目录，任务结束即删（用完即删的临时文件，不需要 TTL 服务）
- **删除"鉴权/限流/并发控制"**：本地后端不需要；云端适配器直接用用户自己的 key，天然没有你的服务器参与
- **第 13 步（本地模型）提到第 10 步之前**：先做本地 ComfyUI 适配器，云端往后放

这样改的好处：**项目从第一天起就是"照片不出机器"的**，隐私承诺不再依赖你自己写的过期删除逻辑是否正确。这对情侣桌宠这种要上传真人照片的场景是决定性的。

### 关于"客户端只拿到临时授权结果"

原方案这句假设了自建后端。改成适配器模式后，这条变成："客户端只从本地进程读取结果，或从用户自己配置的云服务读取结果，**项目方永远不接触用户照片**"。后者的表述更强，也更容易做到。

## 五、问题四：遗漏项

以下 7 项原方案未覆盖，但会实际影响交付：

**1. Wayland 不是"兼容模式"能解决的，需要明确降级策略**

已核实：Wayland 下客户端无法自行控制 Z 序，`_NET_WM_STATE_ABOVE` / `Qt::X11BypassWindowManagerHint` 均被忽略；GNOME/Mutter **对普通客户端直接禁用置顶**，只有 XWayland 客户端能享受 `_NET_WM_STATE_ABOVE`。这不是"置顶偶尔失效"，而是**原生 Wayland 客户端在 GNOME 下无法置顶**。

- 原方案说"Wayland 提供兼容模式"——需要写清楚**兼容模式到底降级成什么**：普通悬浮窗？只能置顶到当前工作区？跟随鼠标？
- 建议提供 `QT_QPA_PLATFORM=xcb` 启动选项，一键切到 XWayland（这是目前唯一能拿到完整置顶体验的办法）
- KDE Plasma 6 支持 layer-shell，置顶体验比 GNOME 好得多 → README 里按 DE 分别说明
- **Wayland 下点击穿透（`WindowTransparentForInput`）不可用**，透明窗口 + 穿透要靠 XWayland

**2. Qt 许可：LGPL vs GPL 的模块选择**

已核实：Qt 6 基础模块（Qt Core / Gui / Widgets / QML / Quick）可用 LGPLv3；但 **Qt Charts、Qt Data Visualization、Qt Purchasing、Qt Virtual Keyboard 仅有 GPLv3 或商业许可**。

若项目要开源（AGPL/MIT 等），**必须避开这几个模块**，否则整个项目被迫 GPLv3。原方案未提及模块许可，这是个会卡在发布前的坑。建议在 `requirements.md` 里写死：**仅使用 LGPLv3 模块，禁止引入 Qt Charts 等 GPL-only 模块**（图表用 QML 自绘即可，桌宠项目本来也不需要复杂图表）。

**3. 素材尺寸与性能预算缺失**

同类项目（VPet）的实测：PNG 序列帧单张 ≤50KB、单组动画 ≤20 帧、推荐 200×300px；WPF 实现下 CPU 1~5%、内存 100~200MB，开透明窗口是性能杀手。

对 Qt 版本应写明预算：
- 桌宠窗口尺寸上限、缩放范围
- 空闲时 CPU 目标（<1%）、内存上限（<150MB）
- 渲染方式：Qt Quick（GPU）与 QWidget+QPainter（CPU）的取舍——桌宠是小尺寸动态图形，**QML Scene Graph 开销可能不划算，用 QWidget + QPainter 反而更轻**，值得在 Sprint 0 后一并验证

**4. 没有"素材制作工具/规范文档"**

第 6 步要产出手工 Q 版角色，但没提**素材规范文档**。这决定了别人能不能给你的项目贡献角色包（这是 GitHub 项目能不能长起来的关键）。至少要有：尺寸规范、锚点表、分层清单、命名规范、校验脚本。

**5. 缺少角色包生态的考虑**

原方案是"用户上传照片 → 自动生成"，但 GitHub 项目要活下去，通常还需要：**官方示例角色包 + 用户自制角色的分发机制**。建议把第 6 步的素材额外做成"可分享的角色包"，附带元数据（作者、许可、适配的 petpack 版本），这是项目从"个人工具"变成"开源项目"的标志。

**6. 双宠互动的位置偏早**

第 7 步做双人桌宠，但那时宠物形象还是占位素材，"送心、击掌、贴贴"这些动作很难做出来（占位角色没有合适的动画帧）。建议：**双宠逻辑的框架可以早搭，但具体的双人动作素材推迟到有真实角色之后**。

**7. 缺少破坏性操作与升级的兼容性测试**

原方案第 14 步提到"旧版配置与旧角色包升级迁移"，但 petpack 若采用带版本号的骨架格式，**需要明确向前兼容策略**（旧 petpack 在新引擎上如何降级运行）。这个要在格式定稿时就想，不是测试阶段才补。

## 六、修订后的实施路线图

```
Sprint 0 验证尖刺（1-2周）      ← 新增，最重要
  └─ 产出：技术选型 + 10~20张测试图 + petpack格式v0.1 + 可复现workflow

Phase 1 桌宠引擎（4-6周）
  └─ 项目骨架 → 透明窗口/托盘/单实例 → 平台能力层 → petpack引擎 → 交互
  └─ 产出：双平台可运行 v0.1（占位角色即可）

Phase 2 角色与生成（4-6周）
  └─ 手工角色包（按分层规范）→ 生成页面 → ComfyUI本地适配器 → 自动切层/绑定 → 我的角色库
  └─ 产出：双平台 v0.5，照片→角色→桌宠全流程跑通

Phase 3 发布与打磨（2-3周）
  └─ 安装包(.exe/.deb/AppImage) → GitHub Actions → Release → 文档/隐私政策 → 测试矩阵
  └─ 产出：GitHub Release v1.0 可下载安装

Phase 4 异地情侣（3-4周）
  └─ 配对 → 送心/状态同步 → 加密与撤销
  └─ 产出：v1.1 双机联动
```

**与原方案的关键差异**：

| 项 | 原方案 | 修订 |
|---|---|---|
| AI 验证时点 | 第 10-12 步 | Sprint 0，最前 |
| petpack 结构 | 帧序列 | 分层 + 骨架 + 关键帧 |
| 后端 | 自建 API+Worker+对象存储 | 本地 ComfyUI 优先，云端可选适配器 |
| 照片流向 | 上传到自有服务器 | 默认不出机器 |
| 打包发布 | 第 8 步（双宠之后） | Phase 3，提前让用户能装 |
| 异地情侣 | 第 15 步（最后） | Phase 4，但前置设计格式预留 |

**调整理由**：把"发布"从第 8 步挪到 Phase 3，是因为**尽早让真实用户装上，才能暴露打包、自启动、Wayland 等环境问题**——这些问题在开发机上永远测不出来。把"异地情侣"放最后但**在 petpack 格式设计时就预留扩展位**（角色 ID、动作扩展、远程触发钩子）。

## 七、Sprint 0 详细执行建议

### 目标（必须回答的 3 个问题）
1. 单张照片能否稳定生成可辨识的 Q 版角色？
2. 能否生成"多姿势但同一角色"？还是必须靠骨架变换？
3. `petpack` 应该是帧序列还是分层骨架？

### 建议路径

**第 1-2 天：环境与基线**
- 装 ComfyUI（本地，本机无 NVIDIA 独显 → 用 CPU 跑小模型或接云 GPU API）
- 准备 3~5 张测试照片（正脸为主，避免大角度侧脸和遮挡）
- 跑通 SDXL 基础文生图 + 确认中文提示词或英文提示词的效果差异

**第 3-5 天：人脸保持**
- 接 IP-Adapter（FaceID）或 InstantID
- 验证：能否保留发型、脸型、眼镜这类辨识度高的特征
- **关键对比**：用 "Q版/SD cartoon/chibi style" 等提示词 vs 用 Chibi LoRA，效果差异大不大？LoRA 通常更稳定

**第 6-8 天：一致性**
- 路线 A：ControlNet OpenPose + 锁定 seed/IP-Adapter 权重，生成 4 个姿态
- 路线 B：生成 1 张标准立绘 → 人工分层 → 写个最小骨架变换 Demo 看效果
- 对比两条路线的实际稳定性

**第 9-10 天：定格式**
- 根据结果定 `petpack` v0.1（分层结构 + rig.json + 动画 JSON schema）
- 写一个格式校验脚本（能加载 petpack 的最小 Python/JS 工具）

**第 11-14 天：收尾**
- 写技术选型文档
- 把 10~20 张测试图归档到 `assets/tests/`
- 整理可复现的 ComfyUI workflow JSON

### Sprint 0 的决策门（Go / No-Go）

| 结果 | 决策 |
|---|---|
| 人脸保持可辨识 + 骨架路线可行 | 按修订路线图推进 |
| 人脸保持可辨识 + 只能靠多图生成 | petpack 改为分层+骨架，生成阶段只出外观层，**放弃 AI 直接出多帧** |
| 人脸保持困难（生成结果不像本人） | **降级方案：提供"上传照片 → AI 生成参考描述/风格提示词 → 人工微调角色"的半自动流程**，或直接做纯手绘工具路线 |

**即使最差结果，Sprint 0 也不浪费**——它同时产出了项目骨架、petpack 格式规范和 CI 流程，这些是后续所有阶段都需要的。
